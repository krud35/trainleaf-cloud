# Planning reserve · prototype convention

`energy-model.js` is pure and does not modify workouts, post-session ratings, load snapshots, references or dates. No production mobile changes. The model is a product heuristic for planning, without scientific or clinical validation. It does not claim readiness, recovery, health, or a recommended training dose.

**Post-audit correction, 2026-10-04:** this is a reversible prototype of the team's working rules, not a replacement for the [production data contract](../../docs/mobile-iteration-3-contract.md). The later team decision D2–D4 supersedes the earlier production fallback to historical planned load: past uncompleted plans and completed physical sessions missing actual load are unknown. Empty past/current dates require explicit confirmation. `historyStart` is ignored, including on old saved demos. Production reference storage remains different. See [HANDOFF-ITERATION-3.md](HANDOFF-ITERATION-3.md#różnice-prognozy--reguły-do-integracji-androida) for the adapter and final-APK retest. These prototype tests do not verify Android or approve heuristic parameters.

**Provenance:** 21 days, half-lives 1/2/3, `B=S/(S+R)` and the indirect-set factor 0.5 were chosen by the team in the user's commissioned research/implementation. They were not separately numerically approved by the user and are not physiologically validated. The user's approved load v1 (`m(x)=0.5+x/10`, weights mental 0, technical 0.6, endurance 0.8, running 1.05, strength 1.3, team 1) and existing snapshots are unchanged.

## APIs

`createReserveReference({workouts,start,end,today,kind})` returns a saved-reference candidate directly, or `{error: Polish message}`. Root must present the candidate and persist it only after explicit user confirmation. Start/end require exactly seven inclusive consecutive calendar days. Kind is `completed` or `planned`. A completed reference must be fully in the past/up to today. It must contain at least one selected session; all selected sessions must have known loads and their sum must be positive. No default reference is created.

Candidate includes `{algorithm:'plan-reserve-v1', value:S, source:{start,end,kind}, capturedOn, sessions, emptyDates, convention:'sum_selected_week_load', lookbackDays:21, halfLifeDays:2, halfLifeScenarios:[1,2,3]}`. `sessions` captures identities, dates, values and sources for review. `emptyDates` contains only dates with no active entries in a completed week; an example planned week returns none. The candidate does not confirm these dates. Only after the UI's explicit confirmation does root save `confirmedComplete:true` and `confirmedRestDays:emptyDates` for a completed reference. Legacy references without those fields still supply S but do not certify rest. **S is the sum of load in the explicitly selected week**; this is a product convention, not physiological capacity. Later rescheduling/editing workouts does not update S.

`forecastReserve({workouts,dates,today,reference,confirmedRestDays})` returns a date-keyed object. Each result contains `{state,status,label,detail,value,lower,upper,knownValue,knownLower,knownUpper,residual,knownResidual,missingCount,missingDays,coverage,days,scenarios,window}`. Numeric balances are fractions, never percentages of readiness in UI. `reference` needs the algorithm, positive finite S and valid source metadata. Missing reference gives `state:'unknown'`, `status:'no-reference'`, label `Ustaw odniesienie`; all full and known balance values are null, while known residual remains diagnostic.

Forecast is at the **start** of each day d. The previous 21 local calendar dates enter; same-day entries do not. UTC arithmetic performs differences between date-only labels to avoid DST shifts. For half-lives h in `[1,2,3]`, `R(d,h)=Σ load(i) * 2^(-(d-i)/h)`, with `d-21 <= i < d`. `B=S/(S+R)`; `value` uses h=2, `lower/upper` span h=1/3 scenarios. The interval is sensitivity to the chosen half-life, not a probability interval.

The forecast explicitly visits all 21 dates. Empty dates <= today are unknown unless in `confirmedRestDays`; valid confirmed dates from a completed, explicitly confirmed reference may also contribute, restricted to its week. Empty future dates are estimated 0, not promised rest. Actual entries always take precedence over a rest confirmation: a past plan or missing actual snapshot keeps that date incomplete. `historyStart` and the first workout date provide no evidence of completeness.

Any unknown day yields `state:'low-confidence'`, `status:'incomplete'`, null `value/lower/upper` and a hatched known-partial bar using `knownValue`. Each scenario keeps full `residual/balance:null` and separate `knownResidual/knownBalance`. The top-level `residual` remains an alias of known residual for old prototype consumers; **do not map it to production full residual**. `days[].load` is null for incomplete days, `knownLoad` retains recorded contributions. `missingCount` counts incomplete sessions; `missingDays` also includes empty unconfirmed days. `coverage` explicitly reports recorded/estimated/unknown days out of 21. This is sensitivity and data completeness, not a confidence interval.

`historyConfirmationDays({workouts,start,end,today})` returns `{dates,blockedDays,start,end}` or `{error}`. It validates ISO inclusive dates through today and a maximum range of 3660 days. Only dates with no canonical active records enter `dates`; it never changes state. Root displays this preview with the required checkbox **W tym okresie mam zapisane wszystkie treningi**. Changing dates clears the checkbox. Saving adds only the empty dates to local `state.confirmedRestDays` and a `historyConfirmations` audit record; failure leaves the selected dates/checkbox in the form. This local format is not a production migration contract. No user must click every day separately, and existing incomplete sessions are not zeroed.

## Record rules

One canonical record per ID. If the newest record is skipped/deleted or has `deletedAt`, it contributes nothing. Otherwise a nonfuture completed record takes precedence over its plan, regardless of input order; revisions/updatedAt choose between actual versions. A newer restored actual may replace an older tombstone. Each anonymous entry stays independent. Nested `workout.planned` never enters the series.

Completed physical records use `loadSnapshot.status === 'calculated'` with a finite nonnegative value. Missing actual snapshot is unknown; duration, RPE, ratings and old planned load do not fill it in. Completed mental sessions have physical load 0 under the approved zero weight; reading does not create/persist a snapshot or historical questionnaire. Future completed records remain unknown, including mental sessions.

Planned physical records on today/future dates require positive duration and explicit `plannedExertion:{aerobic,muscular,source?...}` with both ratings in 0–10. Mental plans retain v1 physical zero without inventing time or physical ratings. A past plan without recorded execution is unknown, including a mental past plan: it is never used as evidence of execution. Planned physical load invokes existing `computeTrainleafLoad` with a temporary completed view and explicit expectations. It never persists that computation as an actual snapshot and never uses actual future post-session ratings. Completion replaces the plan by canonical identity.

An explicitly selected `kind:'planned'` reference may use an example plan at historical dates. This is an intentional reference-only exception via `reserveSessionLoad(...,{allowHistoricalPlan:true})`, never used by forecasts. A completed reference includes actual records only and returns `uncompletedPlanCount` for selected-week plans lacking execution. Root's confirmation should explicitly affirm that all actual sessions are recorded; any unresolved plans should be shown with that count rather than silently represented as execution.

Additional exports `reserveSessionLoad(workout,today)` and `canonicalReserveWorkouts(workouts,today)` support pure tests. `RESERVE_ALGORITHM`, `RESERVE_LOOKBACK_DAYS`, `RESERVE_HALF_LIFE_SCENARIOS` expose constants.

## Verification

`node check-energy.mjs` covers monotonic two-session accumulation, previous Sunday entering Monday, start-of-day exclusion, spring/autumn DST and year boundaries, fixed reference S, canonical actual/plan and tombstone precedence, mental zero without mutation, past plans, missing snapshots without fallback, full vs known results, missing/confirmed/future empty dates, bulk confirmation with occupied days, reference-only confirmation and example-week isolation. Browser QA additionally checks form failure preservation, successful retry, clearing confirmation after a range change and retained incomplete-session labels. These are prototype checks, not final APK, migration or physiological validation.
